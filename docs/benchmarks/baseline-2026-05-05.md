# XDR Decode Microbenchmark Baseline — 2026-05-05

Baseline for the NFSv3 XDR decode hot paths, captured before any
`zerocopy`/decoder rewrite. Re-run with:

```bash
cargo bench --bench xdr_decode
```

## Reading the numbers

- **`READ3resok` is constant time over payload size** (≈ 91 ns regardless of
  4 KiB / 64 KiB / 1 MiB). This confirms the data payload is sliced via
  `Bytes`, not copied — `try_variable_bytes` is `O(1)`. The 4 KiB run shows
  noise from cold-cache effects, not real overhead. **There is no "READ data
  copy" left to remove.**
- **`fattr3` decode ≈ 36 ns** for 84 wire bytes ⇒ ~2.3 GB/s of structured
  decoding. Dominated by 13 sequential `bytes::Buf::get_u32/u64` calls (each
  with a bounds check + bswap).
- **`readdirplus_page` scales linearly** in entry count: 10 entries 1.83 µs,
  100 entries 22.9 µs, 1 000 entries 239.5 µs — roughly 2.0–2.4 µs per 10
  entries. Per-entry cost ≈ 180–240 ns (1× fattr3 + filename slice + fh
  slice + 4 markers). About 15 % of that is the fattr3 decode itself.

## Outlier observations

Several benches have outlier rates 12–17 %. The host is a shared dev box;
results should be re-validated on a quiet machine before drawing strong
conclusions. The relative gaps between bench cases are stable across two
back-to-back runs (the second `cargo bench` reported "No change in
performance detected" for 7 of 8 cases).

## Comparison protocol

Any future optimisation PR should attach a fresh `cargo bench --bench
xdr_decode` capture alongside this baseline. Criterion's auto-comparison
against `target/criterion/<name>/base/` will flag regressions/improvements
and record their statistical significance.

## Decision threshold

From the original `zerocopy` plan: only proceed with a `zerocopy`-based
`fattr3` decoder if `readdirplus_page_decode/1000_entries` accounts for
≥ 30 % of an end-to-end `readdirplus`-heavy workload's wall time. **At
≈ 240 µs / page**, that means a workload would need ≥ 800 µs total per page
spent on decode-bound work for the optimisation to clear the bar — easy to
hit only in pathological pure-CPU loops, hard to hit on real network NFS.
The honest call remains: **collect end-to-end profiles first, do not
preemptively rewrite.**
