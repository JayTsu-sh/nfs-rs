# nfs-rs 读写路径优化：预读 + 回写（FAS2750 复测，2026-09-05）

基于 [2026-09-04 的 nfs-rs vs 内核挂载对比](fas2750-nfsrs-vs-kernel-2026-09-04.md)，本轮实现了报告建议中的前两项优化并同场复测：

1. **顺序预读 / 流水线**（`readahead=8`）：单读者以整块（rsize）顺序读时，提前发出后续 8 个 READ；多路并发（QD>1）或小于整块的读不预读。
2. **回写**（`writeback=8`）：WRITE 改为 UNSTABLE、8 块在途；`flush()`/`close()` 和每 16 MiB 发一次 COMMIT；小写先合并成整块；COMMIT 返回的 verifier 变化时，用保留的未提交数据以 FILE_SYNC 重发；单个小写直接一个 FILE_SYNC 往返。

实现为独立的 `BufferedFile` 层（`src/fileio.rs`），`Mount::read`/`Mount::write` 语义不变；Python 文件对象在任一窗口开启时自动经过该层。`readahead` 默认 8，`writeback` 默认 0（需显式开启：写只在 `flush()`/`close()` 后保证持久）。

## 执行摘要

|---|---|---|---|---|---|
| Rust 写（v3 / v4.0 / v4.1） | 82 / 82 / 81 | **108 / 107 / 106** | 79 / 77 / 79 | 102 / 102 / 102 | 1.34–1.38 |
| Rust 读 | 91 / 91 / 90 | **109 / 109 / 111** | 85 / 89 / 85 | 111 / 108 / 95 | 1.22–1.31 |
| Python 写 | 77 / 74 / 72 | **106 / 105 / 104** | 80 / 81 / 79 | 103 / 103 / 103 | 1.30–1.32 |
| Python 读 | 64 / 63 / 61 | **110 / 109 / 107** | 90 / 66 / 62 | 100 / 98 / 89 | 1.22–1.74 |

- 单路顺序读写从 60–90 MiB/s 提到 104–111 MiB/s，打满 1 Gbps 链路；超过内核 `O_DIRECT` 22–74%，与内核 buffered（预读 + 回写）持平或略高。
- QD8 与 8 进程多客户端不变（都在链路上限 106–111 MiB/s）；8 进程同文件仍是内核 page cache 共享的数量级优势（0.14–0.18）。
- 4 KiB 单次操作持平（差异在 ±0.4 ms 的运行间抖动内）。
- 峰值 RSS：QD1 顺序读写 Rust +12–13 MiB、Python +10–16 MiB（v3/v4.0），上限固定，不随文件大小增长；QD8 和 4 KiB 不变。v4.1 Rust 进程基数更高（52 MiB），见下文。

## 分析

- **QD1 的差距就是"在途块数"。** 优化前单路读写每次只有 1 个 1 MiB RPC 在途，0.28 ms RTT 加服务端处理把吞吐压在 80–90 MiB/s；预读/回写各保持 8 块在途后，与 QD8 一样打满链路。这与昨日 QD8 已达链路上限的结论一致，也说明当前链路下 4 块在途就够（带宽时延积 ≈ 32 KiB），8 块是给 10 GbE 留的余量。
- **Python 读的提升更大（+70%）**，因为 Python 侧的模式校验（memoryview 比较）原本串行在两次 RPC 之间，现在与网络传输重叠。这也是本轮把校验计入计时后 `base` 读只有 61–64 MiB/s 的原因：它反映的是"调用方每读一块要花 4 ms 处理"的真实场景。
- **UNSTABLE + COMMIT 在 ONTAP 上并未额外省事**：NVRAM 让 FILE_SYNC 本来就快，收益来自流水线而非稳定性等级；但代价也小（每 16 MiB 一次 COMMIT ≈ 0.3 ms）。写 verifier 重发路径在测试中未触发（无服务端重启），有单元测试覆盖。
- **多路并发时不预读**是刻意选择：8 个协程按固定步长交错读同一文件时，单一预读窗口无法预测顺序，初版在 Python QD8 上退化到 39 MiB/s、RSS 810 MiB；改为"仅单读者整块顺序读才开窗"后 QD8 恢复 110 MiB/s。调用方需要并发时自己开 QD，两者不叠加。
- **v4.1 Rust 内存**：优化前 QD1 14 MiB、QD8 48 MiB，优化后 QD1 52 MiB、QD8 74 MiB，比 v3/v4.0 高 25–40 MiB。v4.1 每个在途 COMPOUND 占一个会话 slot 并保留回复缓存，在途 READ/WRITE 的 1 MiB 载荷会随之驻留；值得单独排查 slot 表的回复保留策略。
- **未变的部分**：元数据路径（本轮未复测，与优化无关）、8 进程同文件读（需要进程间共享缓存，库内无法解决）。

## 方法

- 与 2026-09-04 相同的 harness、导出、客户端（node181）、内核挂载选项；`run.sh` 增加 `NFSRS_VARIANTS` 在同一轮里跑 nfs-rs 的两个变体，`SKIP_METADATA=1` 跳过元数据。
- **计时修正**：harness 原先把读回后的数据校验耗时从总时长中扣除，这会高估任何把传输与校验重叠的一方（预读、page cache）——昨日报告中 Python 内核 buffered 冷读 165 MiB/s 超过链路上限即此原因。本轮校验计入计时（Rust 为 memcmp，开销 <1%；Python 为 memoryview 比较，约 4 ms/MiB），内核用例同场复测。两日内核 `O_DIRECT` 数字一致（±3%）。
- 4 KiB 与 40 MiB 的 nfs-rs 用例在修正"小读不预读"后用最终二进制（commit `8a0de2c`）以 7 次重复补跑；1 GiB 与多客户端用例来自 commit `d6b1b42`，两者在这些路径上代码相同。
- 原始 JSON：`tests/benchmarks/compare/results/2026-09-05-opt/`（168 个用例，0 失败）；表格由 `report_delta.py` 生成。

## 限制

- 链路 ≈ 1 Gbps：优化后三者都贴着 110 MiB/s，无法区分更高上限下的差异；10 GbE 链路上 QD1 的差距可能重新出现，届时 `readahead`/`writeback` 需要按带宽时延积调大。
- 40 MiB QD1 写的样本双峰（60 / 107 MiB/s，优化前后都有）、4 KiB 延迟运行间抖动 ±0.4 ms：0.4 秒级和亚毫秒级测试对共享 SVM 的存储端抖动敏感，已取 7 次中位数，但单元格级的 ±10% 差异不应过度解读。
- `writeback` 改变了 Python `write()` 的错误语义（错误延后到 `flush()`/`close()`），所以默认关闭；需要吞吐的场景显式开启。
