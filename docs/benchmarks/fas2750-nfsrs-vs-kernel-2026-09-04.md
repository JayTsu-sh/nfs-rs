# nfs-rs vs 内核 NFS 挂载性能对比（FAS2750）

## 执行摘要

所有比值定义为 **nfs-rs 相对内核挂载的相对性能**：1.00 = 持平，0.50 = nfs-rs 慢一倍，2.00 = nfs-rs 快一倍。元数据取 9 种操作 p50 延迟比（内核/nfs-rs）的几何平均；数据路径取吞吐比（nfs-rs/内核 O_DIRECT）；多客户端取 8 路聚合吞吐比（nfs-rs/内核 O_DIRECT）。

## 分析

- **数据路径持平（三种协议一致）。** QD8 下 nfs-rs、内核 O_DIRECT、内核 buffered 全部打满 ~110 MiB/s 链路，1 GiB 读写比值 0.99–1.04；QD1 顺序读写 nfs-rs 79–98 MiB/s 与内核 O_DIRECT 80–88 相当。4 KiB 单次写 1.0–1.3 ms vs 内核 0.83–0.85 ms，读 0.44–0.55 vs 0.53–0.73 ms。Python 封装的数据路径与 Rust API 无可见差距。LIF .201 交叉验证与 .200 一致（±2%）。
- **元数据慢 4–10 倍，根因是没有缓存。** nfs-rs 每个操作 ≈ 1 个 RTT（v3 1.1–1.9 ms、v4.0 1.7–2.9 ms、v4.1 0.9–2.1 ms），内核 default 靠属性缓存把 stat/access 做到 30–40 µs、变更操作 0.5–0.9 ms。与生产常用的 `lookupcache=none` 内核挂载相比，nfs-rs 持平甚至更快（create / rename / remove / chmod 三种协议下都赢）。
- **v4.1 是 nfs-rs 元数据最快的协议。** stat 0.93 ms、access 0.89 ms、chmod 1.03 ms，比 v3 快 30%、比 v4.0 快 45%。
- **多进程读同一文件：内核 page cache 共享是数量级优势。** 8 进程读同一 1 GiB，内核 buffered 590–770 MiB/s，nfs-rs 110 MiB/s，比值 0.14–0.17，与参考报告的 12% 是同一现象。读各自文件时两者都 ~110，持平。
- **库侧问题 1：** Python `listdir` 1000 项 146–162 ms，Rust 同操作 v3 仅 2.7 ms，差 50 倍。
- **库侧问题 2：** Rust readdir 随协议差异大——v3 2.7 ms、v4.1 9.6 ms、v4.0 21 ms（1000 项）。
- **库侧问题 3：** Python `open("wb")` 创建文件 3.6–5 ms vs Rust `create` 1.4–2.9 ms。
- **库侧问题 4：** v4.1 下 nfs-rs 峰值内存 47 MiB（v3 14、v4.0 19 MiB）。
- **观察：** ONTAP v4.1 会话把单次 READ/WRITE 载荷协商成 1044480 B（1020 KiB）；150 用例中出现 1 次 v4.1 会话级瞬时恢复事件（`ReplaySensitive / VerifyThenResume`），重跑即过。

## 方法

- Harness：`src/bin/nfs-perf-compare`（Rust）与 `tests/benchmarks/compare/perf_compare.py`（Python），同 CLI、同 JSON schema；`--target nfs://…` 走 nfs-rs 直连，`--target /mnt/…` 走内核挂载的 POSIX 调用。矩阵驱动 `run.sh`，报告生成 `report.py` / `report_page.py`。
- 内核挂载选项 `vers=X,rsize=1048576,wsize=1048576,hard,proto=tcp`；元数据另跑一遍 `lookupcache=none`。nfs-rs URL `nfs://LIF/nfsrs_perf?version=X&rsize=1048576&wsize=1048576&uid=0&gid=0`。
- 数据路径：按 1 MiB（v4.1 为 1020 KiB）分块写满后 COMMIT / fsync，计时 create→sync；读回按块校验模式数据，校验耗时已扣除。QD8 = 同一文件 8 路 in-flight。冷读前 `sync; echo 3 > drop_caches`。大文件重复 3 次取中位数，4 KiB 200 个文件报 p50/p95。
- 元数据：每次迭代用唯一路径（mkdir → create → stat → access → chmod → rename → remove → rmdir）200 次；readdir 为 1000 项目录 20 次。
- 多客户端：8 个独立进程（各自连接 / 各自打开）完整读 1 GiB，重复 2 次，报聚合吞吐。

## 限制

- **链路 ≈ 1 Gbps。** node181 网卡为 10 GbE，但到 FAS 端到端实测 ≈ 110 MiB/s（内核挂载、`dd`、nfs-rs 一致）。QD8 场景三者都打满链路，差异主要看 QD1 与元数据；换 10 GbE 链路后 QD8 差距可能重新出现。
- **噪声。** node181 同时运行 k3s / ClickHouse / Prometheus（空闲 load ≈ 1.5）；SVM lizy 为多人共用。个别格子（如 python-nfsrs v4.1 40 MiB QD1 写 62 MiB/s）有抖动。
- **NFSv4.1 内核挂载的 trunking 挂起。** SVM lizy 还有 `192.168.13.x` 私网 NFS LIF，Linux v4.1 客户端做 session trunking 发现时会尝试连接它们并长时间挂起（首轮 v4.1 内核用例被拖慢 10–40 倍，已作废重跑）。测试时在 node181 加了 `ip route add unreachable 192.168.13.0/24` 让其快速失败。nfs-rs 只连 URL 指定的 LIF，不受影响。生产环境若 SVM 有客户端不可达的 LIF，内核 v4.1 客户端会遇到同样问题。
- **存储准备。** 专用卷 `/nfsrs_perf`（50 GB，导出策略仅放行 node181，nfs3+nfs4，sec=sys）；SVM `tcp_max_transfer_size` 由 64 KiB 提到 1 MiB（`ontap_prepare.py`，可回滚）。
